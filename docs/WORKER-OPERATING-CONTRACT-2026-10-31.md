Use only available tools and supported timeout options; do not change accounts, credentials, permissions or host-key policy to make the diagnostic succeed.

Classify the evidence before retrying. An explicit connection timeout/reset, unreachable transport, expired connector authentication or SSH authentication failure (for example, SSH `Permission denied (publickey)`) can enter this diagnostic recovery loop. An actual safety, approval or auto-review denial cannot: retain the denied action and stated reason, honor that boundary, and continue unaffected work. A generic permission error or request for interactive input alone does not establish a transient authentication failure. When the owner confirms that authentication has been repaired, a fresh read-only diagnostic is permitted immediately, including after a previous noninteractive/user-input failure that the owner specifically identified as authentication. This refreshes the factual observation; it neither overrides a policy denial nor authorizes replaying the original operation.

Stop on the first success. A later failure episode does not reset this cap. An immediate diagnostic after confirmed repair consumes a remaining retry if this run has already attempted its initial diagnostic. Use an actually available timer, with no individual wait longer than 60 seconds. If no timer is available, or the remaining run budget cannot cover the delay and diagnostic, record the next eligible UTC and defer to a subsequent scheduled run. Never simulate a wait, repeatedly call tools to burn time, loop indefinitely, self-wake or alter task schedules to implement this backoff.

A successful health diagnostic clears only the connection/authentication observation.
